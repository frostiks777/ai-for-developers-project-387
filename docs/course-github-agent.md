## О проекте (общая вставка)

### Чему учимся

Это продолжение проекта «Календарь звонков»: приложение уже написано, и здесь мы переносим работу с
агентом из локальной разработки в GitHub-процесс команды. Агент перестаёт быть помощником в терминале
одного человека и становится участником процесса: отвечает в issue, разбирает задачу, открывает pull
request, вносит правки после ревью и выходит по расписанию с регулярной проверкой.

Устроено это через GitHub App и воркфлоу в .github/workflows/. Событие в репозитории (комментарий,
открытие pull request, срабатывание расписания) запускает агента внутри GitHub Actions, а результат
появляется там же, где идёт работа команды. Шаги проекта идут по этим сценариям по очереди, и каждый
называет, что должно остаться в репозитории после него.

Проверяется в этом проекте процесс. Продуктовая функциональность не растёт, зато остаются следы
работы, которые открываются глазами: прогоны в Actions, ответы агента в issue, pull request с правками
после ревью, сохранённый отчёт регулярной проверки.

### Описание проекта

Репозиторий предыдущего проекта берётся целиком: приложение, тесты, линтеры, прогон в GitHub Actions,
release-please и AGENTS.md. Всё это остаётся рабочим и используется дальше. Агент в GitHub Actions
читает тот же AGENTS.md, а коммиты по Conventional Commits так же собираются в release-PR.

Каждый проект на Хекслете выполняется в своём репозитории, поэтому первым делом код переносится в
новый. Заодно нужен небольшой план развития: одна-две фичи и один-два бага. Дальше по шагам агент
разбирает именно эти задачи, поэтому они должны быть похожи на настоящие: сформулированные как жалоба
пользователя, без готового решения внутри.

## Шаг 2. Установка и настройка агента в GitHub

## Шаг 3. Работа с issue и triage

### Требования

- Есть issue с описанием в виде жалобы пользователя, без готового решения внутри.
- В issue есть команда в комментарии и ответ агента с разбором: причина, затронутые части кода, предлагаемый путь.
- В .github/workflows/ есть воркфлоу автотриажа на событии issues с заданным prompt, и на новой задаче он отработал.
- В issue записано, что считается исправлением: постановка, по которой можно брать задачу в работу.

### Ссылки

- OpenCode GitHub - Supported Events: какие события запускают агента и каким из них обязателен `prompt`.
- OpenCode GitHub - Issues Triage Example: воркфлоу автоматического разбора новых задач.

### Задачи

1. Создайте issue с расплывчатым описанием проблемы в календарном приложении, как её описал бы пользователь.
2. Позовите агента комментарием `/oc explain` и прочитайте разбор.
3. Если разбор полезный, попросите следующий шаг: план исправления или сразу правку через `/oc fix`.
4. Добавьте воркфлоу автотриажа на событии issues с prompt и проверьте его на новой задаче.
5. Сравните два разбора: который получился точнее и почему.
6. Допишите в issue итоговую постановку: что считается исправлением.

### Результат шага

Issue прошёл разбор с участием агента, из нечёткого описания получилась рабочая постановка, а новые
задачи разбираются автоматически при создании.

## Шаг 4. От issue к pull request и ревью

### Требования

- Есть pull request, созданный или обновлённый агентом, и он связан с исходным issue.
- В pull request оставлены оба вида замечаний: общий комментарий в обсуждении и комментарий к строке в diff.
- После замечаний агент внёс правки в ту же ветку, и это видно по коммитам.
- В .github/workflows/ есть воркфлоу авторевью на событии pull_request с prompt, и на pull request он оставил замечания.
- Коммиты агента идут по Conventional Commits, после мержа release-please создал или обновил release-PR.

### Ссылки

- OpenCode GitHub - Pull Request Example: воркфлоу авторевью на открытие pull request.
- Conventional Commits: спецификация формата сообщений коммитов.
- release-please: генерация release-PR с changelog и версией на основе Conventional Commits.

### Задачи

1. В том же issue попросите агента подготовить pull request с исправлением.
2. Проверьте pull request: описание, изменения, связь с issue.
3. Оставьте общий комментарий в обсуждении и комментарий к конкретной строке diff, в каждом позовите агента.
4. Убедитесь, что агент обновил ту же ветку и учёл оба замечания.
5. Добавьте воркфлоу авторевью на событии pull_request с критериями в prompt и посмотрите его замечания на новом pull request.
6. Проверьте формат коммитов агента, мержите pull request и найдите release-PR от release-please.

### Результат шага

Цикл «issue → pull request → ревью → правки → мерж» пройден с участием агента, авторевью работает на
каждый pull request, а после мержа release-please собирает release-PR.

### Статус

- 🟡 PR от агента, связанный с issue, — сверить по истории (`opencode/*`-ветки, `Closes #N`).
- 🟡 Оба вида замечаний — сверить на конкретном PR.
- ✅ Правки в той же ветке видны по коммитам (например, `fix/gcal-link-after-reschedule`).
- ✅ `.github/workflows/opencode-review.yml` (`pull_request: [opened, synchronize, reopened, ready_for_review]` + `prompt`).
- ✅ Conventional Commits, `release-please` формирует release-PR (релизы `v1.0.x` и т.д.).

## Шаг 5. Регулярные задачи по расписанию

### Требования

- В .github/workflows/ есть воркфлоу с событиями schedule и workflow_dispatch, у события schedule задан cron.
- У воркфлоу задан prompt и права contents: write, pull-requests: write, issues: write вместе с id-token: write.
- Частота расписания не чаще одного запуска в сутки.
- Есть хотя бы один успешный прогон, и отчёт проверки сохранён артефактом или опубликован в задаче.
- По находкам отчёта заведён минимум один issue.

### Ссылки

- OpenCode GitHub - Schedule Example: воркфлоу с расписанием и обязательным `prompt`.
- GitHub Actions - Events that trigger workflows: полный список событий, включая `schedule` и `workflow_dispatch`.
- Lighthouse CI - Getting started: запуск проверки скорости страниц из командной строки.

### Задачи

1. Добавьте воркфлоу с schedule и workflow_dispatch, задайте cron с учётом UTC.
2. Пропишите права и prompt: что агент проверяет и что делает с результатом.
3. Настройте сбор данных проверки, например Lighthouse CLI по публичной ссылке приложения. Сам адрес держите переменной репозитория (Settings → Secrets and variables → Actions → Variables), чтобы он не был вписан в воркфлоу.
4. Запустите воркфлоу вручную и добейтесь успешного прогона.
5. Убедитесь, что отчёт сохраняется артефактом или публикуется в задаче, и найдите его через вкладку Actions.
6. Заведите issue по одной из находок отчёта.

### Результат шага

Регулярная проверка работает: воркфлоу запускается по расписанию и вручную, отчёт сохраняется, а по его
находкам появляются задачи.

### Статус

- ❌ Воркфлоу с `schedule`/`workflow_dispatch` в `.github/workflows/` **нет** (шаг не начат).

- В README.md описаны воркфлоу проекта: чем запускаются, какая модель используется и где смотреть прогоны.
- Для публичного репозитория решение по share принято и записано.
- В README.md или в задаче есть короткая самооценка: какие задачи агент закрыл с первого прохода, где потребовались итерации.

### Ссылки

- OpenCode GitHub - Configuration: параметры `model`, `agent`, `variant`, `mentions`, `share`.
