# Каркас приложения

> Источник: [Hexlet — Проект: Календарь звонков, Шаг 2](https://ru.hexlet.io/projects/386/members/53988)

На этом шаге мы собираем каркас: бекенд, фронтенд, тестовый раннер, линтеры и прогон проверок в GitHub Actions. Функциональности здесь пока нет, появляется рабочая основа, на которую дальше кладутся фичи.

Главный ориентир шага — это официальный getting started вашего фреймворка. Открывайте документацию и идите по ней, а команды может выполнять агент. Причина такая: модель помнит прошлые версии инструментов и уверенно предлагает устаревший способ создать проект, подключить сборку или тестовый раннер. Документация фреймворка показывает актуальный способ, и каркас, собранный по ней, потом не приходится разбирать.

Стек вы выбираете сами. Рекомендуем TypeScript и Vite, для интерфейса shadcn/ui или Mantine: с ними агенты дают более точные подсказки, а типы упрощают правки по ходу проекта. Это рекомендация, вы можете взять свои инструменты.

Тестов на функциональность здесь ещё нет, поэтому в CI достаточно одного дымового теста: приложение поднимается и отвечает. Задача шага в том, чтобы прогон тестов и линтера работал автоматически до появления первой фичи.

Тем же заходом подключаем автоматические релизы. Договоритесь о формате сообщений коммитов по спецификации Conventional Commits (`feat:`, `fix:` и так далее) и поставьте release-please отдельным workflow. Он читает историю коммитов, собирает changelog и держит release-PR с версией по правилам семантического версионирования. Формат коммитов касается и тех коммитов, которые пишет агент, поэтому правило записывается в `AGENTS.md`: дальше по проекту коммиты делает в основном он.

В конце шага запустите в агенте команду инициализации (`/init` в OpenCode и Claude Code). Агент изучит собранный каркас и предложит `AGENTS.md`: файл с рабочими правилами проекта, который попадает в контекст в начале каждой сессии. Порядок именно такой: на пустом репозитории инициализации нечего изучать, а после каркаса в проекте уже есть команды запуска, тестов и линтера, и они попадают в файл.

Полученный `AGENTS.md` стоит сократить. Агент почти всегда пишет туда лишнее, а рабочий файл короткий: команды, устройство проекта и правила, которые из кода не читаются.

## Требования

- Бекенд и фронтенд запускаются локально.
- В проекте есть команды запуска тестов и линтера.
- GitHub Actions прогоняет тесты и линтер на каждый push, прогон зелёный.
- Коммиты идут по Conventional Commits, release-please подключён и создаёт release-PR после мержа в основную ветку.
- В корне репозитория есть `AGENTS.md` с командами запуска, тестов и линтера и с правилом про формат коммитов.

## Ссылки

- [AGENTS.md](https://agents.md/): формат файла с рабочими правилами проекта для агентов.
- [Vite](https://vite.dev/): dev-сервер и сборка фронтенда.
- [shadcn/ui](https://ui.shadcn.com/): набор UI-компонентов с гибкой настройкой.
- [Mantine](https://mantine.dev/): готовая UI-библиотека для быстрого старта.
- [shadcn MCP Server](https://ui.shadcn.com/docs/mcp): MCP-сервер, через который агент работает с компонентами shadcn/ui.
- [Conventional Commits](https://www.conventionalcommits.org): спецификация формата сообщений коммитов.
- [release-please](https://github.com/googleapis/release-please): генерация release-PR с changelog и версией на основе Conventional Commits.
- [release-please-action](https://github.com/googleapis/release-please-action): готовый GitHub Action для подключения release-please.

## Задачи

1. Выберите стек и создайте каркас бекенда по getting started вашего фреймворка.
2. Подключите фронтенд и убедитесь, что он собирается и открывается.
3. Подключите тестовый раннер и напишите один дымовой тест.
4. Подключите линтеры.
5. Настройте GitHub Actions: прогон тестов и линтера на каждый push.
6. Подключите release-please отдельным workflow и убедитесь, что после мержа в основную ветку появляется release-PR.
7. Запустите инициализацию агента (`/init`), получите `AGENTS.md`, сократите его до рабочего минимума и запишите правило про формат коммитов.

## Результат шага

Каркас приложения запускается локально, тесты и линтер идут в GitHub Actions, релизы собираются автоматически, в репозитории есть `AGENTS.md`.
