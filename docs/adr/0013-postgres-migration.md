# ADR 0013: Миграция БД с SQLite на PostgreSQL (Neon)

## Status

Accepted — 2026-09-24.

## Context

Изначально проект работал на SQLite (`better-sqlite3`) с файловой БД и in-memory базой в тестах. С ростом числа сущностей (`hosts`, `event_types`, `availability_ranges`, `bookings`) и планами на деплой в облаке выяснились ограничения:

- SQLite-файл на бесплатном Render эфемерный: контейнер пересоздаётся, данные теряются между деплоями.
- Параллельные записи ограничены (один писатель), а часть возможностей Postgres (например, `partial unique index` в нужной форме, типы) отсутствует.
- Требуется внешняя управляемая БД, доступная приложению по одной строке подключения.

Neon — serverless PostgreSQL с бесплатным тарифом и регионом Frankfurt (близко к Render frankfurt).

## Decision

Перевести слой данных на **PostgreSQL**:

- Драйвер — `pg` (node-postgres) через Drizzle ORM (`drizzle-orm/node-postgres`), схема — `drizzle-orm/pg-core`.
- Единственный внешний конфиг БД — `DATABASE_URL` (строка подключения Neon).
- Приложение по-прежнему **Fastify** и хостится на **Render**; Neon используется **только как БД**. Neon Functions и прочий перенос бэкенда в Neon — не применяются.
- Тесты и локальная разработка без внешней БД используют **PGlite** (`@electric-sql/pglite`) — WASM-Postgres в процессе Node, совместимый по SQL-диалекту. Включается, когда `DATABASE_URL` не задан.
- Схема создаётся идемпотентным `runMigrations` (DDL `CREATE TABLE/INDEX IF NOT EXISTS`); колонки camelCase в кавычках, поскольку Postgres чувствителен к регистру идентификаторов.
- Код БД переведён на асинхронный API (все обращения к Drizzle — `await`, `.returning()[0]` вместо `.get()`, `update/delete ... .returning()` вместо `.run()`).
- Переменные окружения валидируются zod-схемой в `server/env.ts` (в т.ч. проверка формата `DATABASE_URL`).
- E2E в CI дополнен отдельным job'ом Playwright (`npx playwright install --with-deps chromium`).

## Consequences

Что становится лучше (+):

- Данные переживают деплой; БД управляемая, с бэкапами (Neon).
- Один и тот же SQL-диалект в тестах (PGlite) и в проде (Neon) — меньше расхождений.
- Zod-валидация env ловит опечатки в переменных окружения на старте.
- `partial unique index` и транзакционная семантика Postgres — ближе к спецификации.

Что становится хуже (-):

- Весь серверный код асинхронный; синхронные `.get()/.run()` больше не работают.
- Локальная разработка «в один процесс без ничего» заменена на PGlite (WASM) или требует `DATABASE_URL`.
- Появилась сетевая зависимость от Neon в проде (латентность, доступность).
- Тесты стартуют чуть медленнее (инициализация PGlite/WASM).

## Alternatives considered

- **Оставить SQLite.** Отклонено: эфемерная ФС Render, ограничения параллелизма и отсутствие управляемых бэкапов.
- **Мигрировать бэкенд в Neon Functions (serverless, Hono).** Отклонено на этом этапе: функции Neon не хостят сайт, требуют переписывания HTTP-слоя Fastify на Hono и отдельного хостинга фронтенда. Цель — только внешняя БД, а не перенос рантайма.
- **Drizzle с PGlite в проде.** Отклонено: PGlite — однопроцессный WASM, не подходит для общего продакшн-доступа.
- **Тесты в отдельной Neon-ветке.** Отклонено ради стабильности CI: PGlite не требует секретов и сети.
