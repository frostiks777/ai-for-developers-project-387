# ADR 0028: Доступ к панели организатора без логина

## Status

Accepted — 2026-09-29.

Заменяет [ADR-0017](0017-dashboard-basic-auth.md) и пункт 1 [ADR-0022](0022-private-bookings-list.md).

## Context

Ревью проверяющего проекта (#88): панель организатора отвечает `401` и требует HTTP Basic Auth — «Панель организатора отвечает 401 и требует Basic Auth. По условиям проекта авторизация не нужна, должен быть один заранее заданный владелец, а проверяющий должен иметь возможность открыть список встреч и управление типами событий. В рамках учебного проекта этот обязательный сценарий нужно сделать доступным без логина».

Проверяющий открывает опубликованный календарь и не может пройти сценарий: не видит ни списка встреч, ни управления типами событий. Это блокирует обязательный сценарий проекта.

Устройство гейта до правки:

- `requiresAdminAuth(method, url)` в `server/app.ts` — список защищённых маршрутов: HTML `/dashboard`, `/admin/*`; легаси-API `/api/availability`, `/api/bookings`, `DELETE /api/bookings/:id`; `POST /api/v1/hosts`; `PUT /api/v1/hosts/:slug/availability`; `GET /api/v1/hosts/:slug/bookings`; `blocks*`; `event-types*` (кроме `GET`).
- `isAuthorizedAdmin` + хук `onRequest` — сверка пароля с `ADMIN_PASSWORD` через `timingSafeEqual`, при неудаче `401` + `WWW-Authenticate: Basic realm="admin"`.
- Гейт включался **только** если `ADMIN_PASSWORD` задан в окружении; в тестах, локальном dev и e2e переменная не задавалась, поэтому гейт молча выключался и не был покрыт обязательными проверками.
- Пароль был в `render.yaml` как демо-значение `call-calendar-admin` и упоминался в README как «Демо-стенд: пользователь `admin`».

Второе следствие: `GET /api/v1/hosts/:slug/bookings` был закрыт гейтом именно из-за [ADR-0022](0022-private-bookings-list.md) (не публиковать имена и email гостей). Снятие гейта означает, что этот список снова читается без пароля.

## Decision

1. **Гейт панели удалён.** Удаляются `requiresAdminAuth`, `isAuthorizedAdmin` и хук `onRequest`, требовавший Basic-auth. Открыты: `/dashboard`, `/admin/*`, `/api/availability`, `/api/bookings`, `DELETE /api/bookings/:id`, `POST /api/v1/hosts`, `PUT /api/v1/hosts/:slug/availability`, `GET /api/v1/hosts/:slug/bookings`, `blocks*`, `event-types*`.
2. **`ADMIN_PASSWORD` больше не участвует.** Переменная удалена из схемы `server/env.ts`, из `.env.example`, из `render.yaml` и из README. Если она осталась в окружении (например, в Environment Group на Render), сервер её игнорирует.
3. **Владелец один и заранее задан** — это уже верно проекту: дефолтный хост сидируется в `server/db/migrate.ts` (`slug: 'default'`), а выбор организатора на клиенте переключает `activeSlug` ([ADR-0021](0021-active-host-and-hosts-ui.md)). Отдельная сущность «пользователь» не вводится.
4. **Тест контракта переписан** — `server/admin-auth.test.ts` → `server/dashboard-access.test.ts`: панель, список встреч, управление типами событий и блокировками отвечают не `401` **даже при заданном `ADMIN_PASSWORD`**, публичные маршруты гостя не сломаны, `/events` по-прежнему перенаправляется в `/admin/bookings`.
5. **Что осталось защищённым:**
   - `POST /api/internal/reminders` — под `X-Reminders-Secret`, без секрета отвечает `404` ([ADR-0026](0026-email-notifications.md)). Это машинный эндпоинт для внешнего cron, а не доступ организатора.
   - публичная запись — Cloudflare Turnstile (fail-closed) и rate-limit по IP ([ADR-0025](0025-captcha-and-rate-limit.md)).
   - отмена и перенос брони — по `cancelToken` (capability-модель, [ADR-0006](0006-cancellation-by-token.md)).

Схема БД, API-контракт (`api/main.tsp`) и сгенерированные артефакты не меняются.

## Consequences

**+** Обязательный сценарий проверяющего доступен: список встреч и управление типами событий открываются сразу.
**+** Нет пароля в Blueprint и README — нечего «менять на проде», исчезает риск демо-пароля в открытом репозитории.
**+** Поведение одинаково в проде, dev, тестах и e2e: раньше гейт молча выключался без `ADMIN_PASSWORD`, и его рабочее поведение почти ничем не проверялось.
**−** `GET /api/v1/hosts/:slug/bookings` снова читается без пароля: имена и email гостей видны любому, кто знает slug хоста. Это откатывает мотивацию [ADR-0022](0022-private-bookings-list.md) (его п. 2 и 3 — редирект `/events` и снятие вкладки из меню — остаются в силе, сама страница `/events` по-прежнему не отдаёт гостю список).
**−** Любой посетитель может менять настройки доступности, типы встреч и блокировки. Для учебного проекта это приемлемо и прямо требуется условиями.
**−** Если в окружении остался `ADMIN_PASSWORD`, он больше не даёт никакой защиты — полагаться на него нельзя.

## Alternatives considered

- **Оставить Basic-auth как необязательный дополнительный доступ (задаётся переменной, по умолчанию выключен).** Отклонено: проверяющий всё равно должен знать, что переменная не задана, иначе снова упрётся в `401`; плюс остаётся мёртвый код гейта и пароль в окружении. Проверяющий просил доступ без логина, а не «два режима».
- **Заменить Basic-auth на сессии/аккаунты.** Отклонено: прямо противоречит условиям проекта («авторизация не нужна») и добавляет сущности, которых в задании нет.
- **Скрыть панель, но оставить API открытым.** Отклонено: проверяющий умеет открывать опубликованный календарь, а скрытый маршрут — это тот же барьер, только нечестный.
- **Оставить `ADMIN_PASSWORD` в env как заглушку «на будущее».** Отклонено: переменная без поведения вводит в заблуждение при чтении `.env` и README.
