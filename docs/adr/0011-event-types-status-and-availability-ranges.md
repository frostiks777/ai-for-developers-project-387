# ADR 0011: Типы встреч, статусы брони и диапазоны доступности

## Status

Accepted — 2026-09-24.

## Context

Шаг 2 приводит домен к ТЗ (`docs/code_artifact.md`): организатор предлагает несколько **типов встреч**, гость выбирает тип и слот, а занятость не допускает двух активных записей на одно время даже для разных типов. ТЗ также заводит `status: confirmed|cancelled` и диапазоны времени по дням недели. Текущий MVP живёт на одном неявном типе, одном окне доступности (`windowStartHour`–`windowEndHour`) и отмене через удаление строки (`DELETE`, ADR-0005/0006) с `UNIQUE(slotId)` (ADR-0003). Эти расхождения нельзя закрыть обратимо: они меняют схему БД, семантику отмены и фильтрацию слотов.

## Decision

- **Типы встреч.** Таблица `event_types`: `id`, `host_id`, `slug` (уникален в пределах хоста), `title`, `description` (nullable), `duration_min` (=30 в MVP), `location_type` (`online` | `offline` | `phone`), `is_active`. Гость на `/book/:slug` видит список активных типов и выбирает один → тот же экран с календарём; в API `eventTypeId` передаётся при запросе слотов и в теле брони. Тип с `duration_min ≠ 30` в MVP скрыт.
- **Статусы брони.** `bookings` получает `status` (`confirmed` | `cancelled`) и `eventTypeId` (FK). Отмена переводит бронь в `cancelled`, а не удаляет строку. Уникальность слота становится **partial unique index** (`UNIQUE(slotId) WHERE status != 'cancelled'`), поэтому отменённая бронь не блокирует повторную запись.
- **Диапазоны доступности.** Правило доступности задаётся списком диапазонов по дням недели (несколько интервалов на день) вместо одного окна.

## Consequences

(+) Домен совпадает с ТЗ; «одно время — одна активная бронь» работает для разных типов.
(+) Диапазоны по дням убирают искусственное ограничение «одно окно».
(+) История сохраняется: отменённые брони остаются в БД со статусом.
(-) Миграция SQLite: создать `event_types`, добавить `status`/`eventTypeId` в `bookings`, заменить `UNIQUE(slotId)` на partial index (пересборка/`CREATE INDEX`), преобразовать одно окно в диапазоны.
(-) Дашборд и токен-отмена меняют семантику: удаление → смена статуса; фильтры списка слотов/броней обязаны исключать `cancelled`.
(-) Частично затрагивает ADR-0003 (индекс), ADR-0005/0006 (отмена удалением).

## Alternatives considered

- **Оставить один неявный тип** — не проходит приёмку курса (тип встречи в сквозном сценарии).
- **Отмена удалением без статуса** — проще, но ТЗ явно требует `status` и историю; отклонено пользователем.
- **Слоты, привязанные к типу** — усложняет генерацию и допускает совпадение времён разных типов; отклонено.
- **Одно окно доступности** — сохраняет MVP, но не даёт перерывов/нескольких смен; отклонено пользователем.
