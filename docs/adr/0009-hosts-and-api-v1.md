# ADR 0009: Хосты и версионированный API v1

## Status

Accepted — 2026-09-23.

## Context

Спека (`docs/code_artifact.md`) описывает мульти-хост: таблицу `hosts`, брони с `host_id` и версионированные эндпоинты `GET /api/v1/hosts/:slug/settings`, `GET /api/v1/hosts/:slug/slots`, `POST /api/v1/bookings`. Текущий MVP — однохостовый: слоты и правила доступности глобальны, API живёт без версии (`/api/*`), [ADR-0005](0005-dashboard-availability-and-cancellation.md) сознательно отложил `hosts`/`/api/v1`.

Полная переработка под мульти-хост (UUID-ключи, `host_id` во всех таблицах, статусы броней, авторизация) — это переписывание существующего контракта и большой риск регрессий. Нужен инкремент, который (а) вводит сущность хоста, (б) даёт версионированный API, (в) не ломает текущий фронтенд.

## Decision

Добавляем аддитивный слой `hosts` + `/api/v1`, существующий `/api/*` не трогаем.

- **Схема.** Новая таблица `hosts` (`id TEXT PK` — UUID, `slug TEXT UNIQUE`, `name`, `timezone`, `createdAt`). При старте сидируется один дефолтный хост (`slug = 'default'`, `name = 'Организатор'`, `timezone = 'UTC'`) — см. `server/hosts.ts`.
- **API v1.**
  - `GET /api/v1/hosts/:slug/settings` → `HostSettings`: данные хоста + текущие `AvailabilityRules`. `404`, если slug неизвестен.
  - `GET /api/v1/hosts/:slug/slots` → `TimeSlot[]`; необязательные `?date=YYYY-MM-DD` и `?timezone=IANA`. Фильтрация по дате выполняется в запрошенном поясе (`?timezone`, иначе `hosts.timezone`); `400` — на некорректную дату или неизвестный пояс, `404` — на неизвестный slug.
- **Без изменений контракта MVP.** `slots`/`bookings`/`availability_rules` остаются глобальными; `host_id` в них не появляется. `/api/*` продолжает работать как раньше.
- **Общий код.** Выборка будущих слотов вынесена в `selectFutureSlots()` внутри `server/app.ts` и переиспользуется `/api/slots` и `/api/v1/.../slots`.

## Consequences

- (+) Появляется сущность хоста и версионированный API — основа для мульти-хост-модели спеки.
- (+) Полностью обратно совместимо: текущий фронтенд и его тесты не меняются.
- (+) Дефолтный хост покрывает однохостовый сценарий без дополнительной настройки.
- (−) Мульти-хост пока «однохостовый по факту»: `bookings.slotId` не привязан к хосту, кросс-хостовой изоляции нет.
- (−) `slots` и `hosts` не связаны FK: слоты не «принадлежат» хосту, а считаются общими.
- (−) `POST /api/v1/bookings` из спеки не реализован — отложен до перевода записей/слотов на `host_id`.

## Alternatives considered

- **Полная миграция на мульти-хост (UUID/`host_id`/статусы) одним шагом.** Отклонено: ломающее изменение схемы и контракта, требует переписывания фронтенда, тестов и seed-логики; риск не оправдан для учебного MVP.
- **`hosts` с автогенерируемым `INTEGER` PK, как у `slots`/`bookings`.** Отклонено: спека предполагает UUID, а slug — естественный публичный идентификатор; UUID не ломает существующие таблицы.
- **Хранить правила доступности в `hosts`.** Отклонено на этом шаге: правила — одна строка ([ADR-0005](0005-dashboard-availability-and-cancellation.md)); перенос в per-host — часть будущей мульти-хост-модели.
- **Сразу добавить `/api/v1/bookings`.** Отклонено: без `host_id` в `bookings` эндпоинт дублировал бы текущий `POST /api/bookings` без выгоды.
