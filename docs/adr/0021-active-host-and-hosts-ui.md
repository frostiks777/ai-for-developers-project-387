# ADR 0021: Активный организатор на клиенте и UI управления хостами

## Status

Accepted — 2026-09-25.

## Context

После [ADR-0018](0018-multi-host-model.md) и [ADR-0020](0020-per-host-availability-rules.md) бэкенд полностью мульти-хостовый: слоты, брони, правила и диапазоны изолированы по `hostId`, есть `GET/POST /api/v1/hosts`. Но фронтенд по-прежнему хардкодил одного организатора — `host.slug = 'default'` в `src/config/host.ts`: лендинг, `/events`, «Мои встречи», панель и её секции всегда обращались к дефолтному хосту, а управлять хостами можно было только через API.

Нужен сквозной UI мульти-хост: активный организатор на всём фронте, выбор/создание хостов в панели.

## Decision

1. **Контракт.** В `api/main.tsp` добавлены модели `Host`, `CreateHostRequest` и операции `GET /api/v1/hosts` (список), `POST /api/v1/hosts` (создание, `201`); SDK и `server/generated` регенерируются одной командой `npm run api:generate` (Design First).
2. **Доступ.** `GET /api/v1/hosts` — **публичное чтение** (как `GET availability/event-types/bookings`); `POST /api/v1/hosts` остаётся админским (Basic-auth). Так публичные страницы могут резолвить активного организатора без пароля.
3. **Активный организатор на клиенте.** `HostProvider` (`src/components/host-provider.tsx`) один раз тянет список хостов и хранит `activeSlug`; выбор сохраняется в `localStorage` (`call-calendar-active-host`, `src/hooks/use-active-host.ts`). Если сохранённый хост отсутствует или хранилище пусто — активен первый хост из списка. Хук `useActiveHost()` контекста даёт дефолт ('default'), поэтому юнит-тесты страниц работают без провайдера.
4. **Весь фронт на активном хосте.** `src/config/host.ts` больше не содержит `slug` (только брендинг/фолбэки). Лендинг, `/events`, `/my`, `/booking/:uuid/confirmed`, `/cancel|/reschedule/:token` и панель используют `activeSlug` (а где есть данные брони — её `hostSlug`). `/book/:slug` берёт slug из URL.
5. **Панель.** `HostSelect` (dropdown «Организатор») в шапке панели; секция `#hosts` «Организаторы» (`HostsEditor`) со списком, подсветкой активного и формой создания. Маршрут `/admin/hosts` открывает секцию (десктоп — скролл, телефон — таб). Все секции панели скоупятся активным хостом и перезагружаются при его смене.
6. **Роутинг `/book/:slug`.** `BookingRoute` считает хост известным, если он есть в списке (по `slug` или `id`), иначе показывает 404. Пока список грузится — не мигает 404.

## Consequences

**+** Полноценный мульти-хост в UI: выбор и создание организаторов, изоляция разделов панели.
**+** Активный хост общий для всего приложения и переживает перезагрузку (`localStorage`).
**+** Контракт — источник истины: hosts CRUD в SDK, а не ручные fetch.
**−** `GET /api/v1/hosts` раскрывает список slug/имён хостов публично (для MVP приемлемо — эти страницы и так публичны).
**−** Активный хост — понятие конкретного браузера; у другого посетителя по умолчанию первый хост.
**−** `BookingRoute` зависит от загрузки списка хостов; при недоступном API известным считается только UUID (эвристика), иначе — 404.

## Alternatives considered

- **Держать `GET /api/v1/hosts` админским и не давать публичным страницам резолвить хост.** Отклонено: тогда «весь фронт» не может показать активного организатора без авторизации.
- **Хранить активный хост на сервере (сессия/настройка).** Отклонено: нет аутентификации гостя, а понятие «активный» — это выбор конкретного управляющего в браузере.
- **Отдельная страница создания хостов вместо секции панели.** Отклонено по решению интервью: секция панели даёт скоупинг и переключение в одном месте.
