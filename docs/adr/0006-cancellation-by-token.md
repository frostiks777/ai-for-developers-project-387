# ADR 0006: Отмена брони по токену-ссылке

## Status

Accepted — 2026-09-23.

## Context

Спека (`docs/code_artifact.md`, §3 «Экран 3») требует на экране успеха «ссылку на отмену или перенос». К этому моменту отмена была доступна только организатору из `/dashboard` ([ADR-0005](0005-dashboard-availability-and-cancellation.md)) через `DELETE /api/bookings/:id`. У гостя, оставившего бронь, не было способа отменить её самостоятельно: у него нет ни авторизации, ни доступа к панели.

Авторизации в проекте нет, поэтому «владелец» брони должен доказываться не логином, а секретом-возможностью (capability).

## Decision

Выдавать каждой брони случайный **токен отмены** и отменять по нему без авторизации.

- **Хранение.** Колонка `bookings.cancelToken TEXT` (nullable, `UNIQUE`). Nullable — потому что у броней, созданных до этого решения, токена нет; `UNIQUE` в SQLite не конфликтует на нескольких `NULL`. Токен — `crypto.randomUUID()` при `INSERT` в `POST /api/bookings`.
- **Выдача.** Токен возвращается **только** в ответе `201` на создание брони (`CreatedBooking extends Booking`). `GET /api/bookings` (панель организатора) токен не отдаёт, чтобы не утекал в списках/логах.
- **Отмена.** `POST /api/bookings/cancel` с телом `{ token }`: `204` при успехе, `404` — если токен неизвестен, `400` — если токена нет в теле. Токен одноразовый по факту: после удаления строки повторная отмена даёт `404`.
- **Ссылка.** Экран успеха показывает `${origin}/cancel/:token` (readonly-поле + кнопка «Скопировать»). Страница `/cancel/:token` не отменяет автоматически при открытии (защита от префетча/сканеров): сначала кнопка «Отменить встречу».
- **Миграция.** Для существующих БД — `ALTER TABLE bookings ADD COLUMN cancelToken TEXT` + `CREATE UNIQUE INDEX IF NOT EXISTS`. Порядок в `server/db/index.ts` важен: индекс создаётся **после** добавления колонки (иначе на старой БД `no such column`).

## Consequences

- (+) Гость может отменить встречу без аккаунта; слот освобождается, `UNIQUE(slotId)` не мешает.
- (+) Токен — не в списках, только у того, кто создал бронь; утечка ограничена одной бронью.
- (+) Не требует auth-инфраструктуры; согласуется с временным отсутствием авторизации.
- (−) Токен в URL может попасть в историю браузера, `Referer` и логи — стандартный риск capability-ссылок. Для учебного MVP принято; при появлении auth токен-ссылку можно заменить/дополнить.
- (−) Отмена неаутентифицирована: любой, у кого есть ссылка, может отменить. Это и есть задуманная модель (как у Calendly в письме-подтверждении).
- (−) Перенос (reschedule) не реализован — только отмена; спека упоминает оба.

## Alternatives considered

- **Отмена по `id` без токена.** Отклонено: `id` — последовательный и угадываемый, любой смог бы отменять чужие брони.
- **JWT/HMAC-подпись `id`.** Даёт то же свойство (неподделываемость) без колонки в БД, но требует секрет в env и реализации подписи/проверки. UUID-токен в БД проще и не зависит от секрета; для MVP выбран он.
- **Обязательная авторизация гостя.** Отклонено: противоречит сценарию «бронь без регистрации» из спеки.
- **Авто-отмена при открытии `/cancel/:token` (GET).** Отклонено: ссылку могут открыть почтовые сканеры/превью, что отменило бы бронь случайно. Отмена — по явному действию (POST).
- **Токен не в URL, а в теле после ввода.** Отклонено: тогда нет «ссылки», которую просит спека.
