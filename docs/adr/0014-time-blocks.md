# ADR 0014: Ручные блокировки времени (time_blocks)

## Status

Accepted — 2026-09-24.

## Context

Организатору нужно закрывать для записи произвольные интервалы — отпуск, личные дела, обучение — без оформления брони на выдуманного гостя и без изменения недельного расписания доступности. Внешняя спека (§3.3) называет это `BlockTimeModal`.

Ранее такой возможности не было: слоты генерировались строго по правилам доступности, и убрать точечный интервал можно было лишь правкой расписания целиком.

## Decision

Вводим сущность «блокировка времени»:

- Таблица `time_blocks`: `id`, `hostId` → `hosts`, `startAt`, `endAt` (UTC ISO), `reason` (nullable), `createdAt`. Одна строка — один интервал.
- API v1: `GET /api/v1/hosts/:slug/blocks`, `POST /api/v1/hosts/:slug/blocks` (`201`), `DELETE /api/v1/hosts/:slug/blocks/:blockId` (`204/400/404`). Схема тела — zod `createTimeBlockSchema` (валидные даты, `endAt > startAt`, причина ≤ 500).
- Блокировка применяется **на чтении**, без удаления слотов: `selectFutureSlots()` исключает слоты, пересекающиеся с любой блокировкой; `POST .../bookings` и `POST .../bookings/:id/reschedule` отвечают `409 CONFLICT` «Время заблокировано организатором» для заблокированного слота.
- Пересечение интервалов [a.start, a.end) и [b.start, b.end) — полуинтервалы (`start < end' && start' < end`), вынесено в чистые функции `overlaps`/`isBlocked` (`server/time-blocks.ts`) и покрыто тестами.
- UI: `BlocksEditor` + `BlockTimeModal` в панели организатора (десктоп-секция «Блокировки времени» и мобильный таб).

## Consequences

Что становится лучше (+):

- Гибкое расписание: точечные исключения (праздники, отпуск) без правки недельного шаблона.
- Слоты не удаляются — блокировку можно снять, и расписание восстанавливается само (слоты остаются в БД).
- Чистые функции пересечения легко тестируются и переиспользуются.

Что становится хуже (-):

- `selectFutureSlots()` делает дополнительную выборку блокировок и фильтрацию в памяти (при нашем объёме — ≤ ~112 слотов — приемлемо).
- Появляется ещё одна таблица и набор эндпоинтов в контракте.
- Блокировка и правило доступности могут конфликтовать концептуально; приоритет — блокировка (она только запрещает).

## Alternatives considered

- **Удалять слоты под блокировкой.** Отклонено: снятие блокировки не вернуло бы слоты без повторной генерации, а занятые слоты трогать нельзя.
- **Хранить блокировки в правилах доступности как «негативные» интервалы.** Отклонено: смешивает недельный шаблон и разовые исключения, усложняет генерацию.
- **Фильтровать блокировки в SQL по `startAt`.** Отклонено как преждевременная оптимизация: при малом горизонте фильтрация в памяти проще и не требует сложного join.
