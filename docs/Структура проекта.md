# Архитектура агентной системы

> Источник: [Hexlet — Практика разработки с ИИ](https://ru.hexlet.io/courses/ai-assisted-development-workflow/lessons/agent-system-architecture/theory_unit)

Правила поведения через `AGENTS.md`, управление контекстом, инструменты, MCP, skills и субагенты — это отдельные части агентной разработки. Теперь соберем все это в единую картину. Как устроен coding-агент изнутри и почему качество результата определяется не одной LLM, а всей системой целиком.

## Из чего состоит coding-агент

Coding-агент — это система из нескольких компонентов, каждый из которых отвечает за свою часть работы.

**Model** — языковая модель, которая рассуждает, интерпретирует задачу и генерирует решения. Она принимает решения о том, какой инструмент вызвать, какой файл прочитать и какой код написать. Модель — это «мозг» системы, но без остальных компонентов она бесполезна для реальной разработки.

**Execution loop** — цикл выполнения, который превращает рассуждения модели в действия. На каждом шаге цикла модель получает текущее состояние, решает, что делать дальше, формирует вызов инструмента, получает результат и переходит к следующему шагу. Этот цикл работает до тех пор, пока модель не решит, что задача выполнена, или пока не будет остановлен пользователем.

**Context manager** — компонент, который управляет тем, что модель видит в каждый момент времени. Он собирает системные инструкции, правила проекта, историю диалога и результаты инструментов. Он же отвечает за упаковку контекста, за загрузку skills и за ограничение размера окна.

**Tools** — набор инструментов для взаимодействия с внешним миром: чтение файлов, поиск, редактирование, shell, MCP-серверы.

**Workspace** — рабочее пространство проекта: файловая система, git-дерево, текущие изменения, состояние тестов. Агент работает с реальным проектом в конкретном состоянии.

**Config** — конфигурация поведения: `AGENTS.md`, skills, определения субагентов, права доступа, подключенные MCP-серверы.

## Execution loop

Центральный механизм агента — цикл выполнения. Каждая задача проходит через последовательность шагов, которая повторяется до завершения.

```
Понять задачу → Спланировать → Изменить → Проверить → Ошибка? → да → (повтор) → нет → Задача выполнена
```

На этапе понимания агент исследует код: ищет файлы, читает реализацию, разбирается в зависимостях. На этапе планирования формулирует, что именно нужно изменить. На этапе изменения вносит правки через edit, create или shell. На этапе проверки запускает тесты, линтер или сборку.

Если проверка показала ошибку, цикл повторяется. Агент читает сообщение об ошибке, находит причину и пробует исправить. Это может повториться несколько раз. Хорошие агенты умеют отличить ситуацию, когда нужно попробовать другой подход, от ситуации, когда нужно остановиться и спросить пользователя.

На практике этот цикл работает не как жесткий алгоритм, а как рекомендуемая последовательность. Модель может пропустить этап планирования для простой задачи или вернуться к исследованию посреди реализации, если обнаружит неожиданную зависимость. Гибкость цикла — одно из ключевых отличий агента от линейного скрипта.

## Управление контекстом как часть архитектуры

Управление контекстом — отдельная задача, которая определяет качество работы агента. В окне агента живут системные инструкции, правила проекта, описания инструментов, история диалога и результаты вызовов. Все это конкурирует за ограниченное пространство. Архитектурные решения, которые агенты используют для управления контекстом:

**Автоматическая упаковка.** Когда история диалога вырастает, агент сжимает ее до краткого резюме. В некоторых системах за это отвечает отдельный внутренний агент, который читает длинную историю и создает короткую выжимку с ключевыми фактами и текущим состоянием задачи. Конкретная реализация отличается, но принцип общий: старое сжимается, чтобы освободить место для нового.

**Ленивая загрузка.** Skills и MCP-серверы не загружают все свое содержимое в контекст сразу. Агент видит только их имена и описания. Полное содержимое подгружается только когда агент решает, что оно нужно для текущей задачи.

**Делегирование субагентам.** Тяжелое исследование уходит субагенту с отдельным контекстом. Обратно приходит краткий результат. Основное окно остается чистым.

**Внешнее состояние.** Todo-списки, промежуточные заметки и планы хранятся вне контекстного окна. Агент обращается к ним по необходимости, а не держит в памяти постоянно.

## Надежность

Для работы с реальными проектами агенты должны генерировать надежные решения. Вот как архитектура агента справляется с ошибками.

**Debug loop.** Когда тесты падают или сборка ломается, агент не останавливается, а входит в цикл отладки: читает ошибку, находит причину, вносит исправление, снова проверяет. Количество итераций ограничено, чтобы агент не зацикливался.

**Ограничение действий.** Деструктивные операции (удаление файлов, выполнение неизвестных shell-команд) могут требовать подтверждения или находиться в deny-листе — зависит от настроек конкретной системы. Разделение на агентов с разным уровнем доступа (например, read-only агент для планирования и полноценный агент для реализации) позволяет ограничить риск случайных изменений.

**Наблюдаемость.** Каждый вызов инструмента логируется. Пользователь видит, что агент делает на каждом шаге, и может вмешаться. Некоторые агенты поддерживают hooks — возможность запускать произвольные действия после определенных событий: например, прогонять prettier после каждого редактирования файла.

**Границы автономности.** Хорошая архитектура предполагает, что агент не должен быть полностью автономным. Он работает как помощник, который берет на себя рутину, но ключевые решения оставляет человеку. Режимы с разным уровнем самостоятельности позволяют настроить баланс: от «только показывай план» до «делай все сам».

## Как все работает вместе

Финальная картина выглядит так. Разработчик дает задачу агенту. Агент загружает контекст: системные инструкции, `AGENTS.md`, описания tools и MCP-серверов. Из описаний skills и субагентов он понимает, какие дополнительные возможности доступны.

```
Разработчик
     │
     ▼
"Добавь OAuth в проект"
     │
     ▼
┌─────────────────────────────────────────────┐
│  Agent                                      │
│                                             │
│  1. Загрузить контекст                      │
│     system prompt + AGENTS.md + tools       │
│                                             │
│  2. Исследовать                             │
│     субагент → текущая auth-система         │
│                                             │
│  3. Спланировать                            │
│     декомпозиция на 4 шага                  │
│                                             │
│  4. Реализовать                             │
│     edit src/auth/oauth.ts                  │
│     edit src/auth/config.ts                 │
│     create src/auth/providers/github.ts     │
│                                             │
│  5. Проверить                               │
│     bash: make test → 2 failures            │
│     → debug loop → fix → make test → ok     │
│                                             │
│  6. Финализировать                          │
│     git diff → предложить commit / PR       │
│                                             │
└─────────────────────────────────────────────┘
     │
     ▼
Pull Request → Code Review → Merge
```

Важно понимать: ни один из этих компонентов не работает сам по себе. Даже самая мощная модель не даст хорошего результата без правильного контекста. Даже идеальный контекст бесполезен без инструментов для действий. Даже лучшие инструменты не помогут, если нет понятных правил и ограничений. Качество агентной разработки определяется тем, как все эти детали собраны вместе.
