# Принципы работы coding-агента

Этот документ — переработанная своими словами теория урока Хекслета «Архитектура агентной системы». Он объясняет, из чего состоит агент, как он выполняет задачи и почему результат зависит от всей системы целиком, а не только от модели.

## Компоненты coding-агента

Агент — это не «голая» LLM, а система из нескольких частей. Качество работы определяется их связкой.

**Model** — языковая модель, «мозг» системы. Она рассуждает о задаче, выбирает следующий шаг, решает, какой инструмент вызвать и какой код написать. Сама по себе модель ничего не делает с реальным проектом — ей нужны остальные компоненты.

**Execution loop** — цикл выполнения, превращающий рассуждения в действия. На каждой итерации модель видит текущее состояние, принимает решение, вызывает инструмент, получает результат — и цикл идёт дальше, пока задача не будет выполнена или пока пользователь не остановит работу.

**Context manager** — управляет тем, что попадает в окно контекста: системные инструкции, правила проекта, история диалога, результаты инструментов. Отвечает за упаковку контекста, подгрузку skills и укладку в ограниченный размер окна.

**Tools** — инструменты взаимодействия с внешним миром: чтение и редактирование файлов, поиск, shell, MCP-серверы. Без них модель может только генерировать текст, но не менять проект.

**Workspace** — реальное рабочее пространство: файловая система проекта, git-дерево, незакоммиченные изменения, состояние тестов. Агент всегда действует поверх конкретного состояния проекта.

**Config** — конфигурация поведения агента: права доступа, подключённые MCP-серверы, определения субагентов, skills и **`AGENTS.md`**. Именно через `AGENTS.md` проект передаёт агенту свои правила: команды, структуру, конвенции — всё то, что не читается напрямую из кода. Это делает `AGENTS.md` частью конфигурации системы, а не просто документацией для людей.

## Цикл выполнения

Любая задача проходит через повторяющийся цикл:

```
Исследование → Планирование → Изменение → Проверка → Ошибка? → да → (повтор) → нет → Готово
```

1. **Исследование** — агент знакомится с кодом: ищет файлы, читает реализацию, разбирает зависимости.
2. **Планирование** — формулирует, что конкретно нужно изменить.
3. **Изменение** — вносит правки: редактирует и создаёт файлы, выполняет команды.
4. **Проверка** — запускает тесты, линтер, сборку или проверку типов.

Если проверка упала, агент читает ошибку, ищет причину и пробует снова — это **debug loop**, вложенные итерации цикла. Важный навык — отличать ситуацию «нужен другой подход» от ситуации «пора остановиться и спросить человека».

Цикл — не жёсткий алгоритм, а рекомендуемый порядок. На простой задаче этап планирования можно пропустить; при неожиданной находке посреди реализации — вернуться к исследованию. Эта гибкость и отличает агента от линейного скрипта.

## Управление контекстом

Окно контекста ограничено, а места в нём хотят все: системные промпты, правила проекта, описания инструментов, история диалога, выводы команд. Архитектура агента решает эту конкуренцию несколькими приёмами:

**Автоматическая упаковка.** Когда история разрастается, она сжимается в короткое резюме с ключевыми фактами и текущим состоянием задачи. Старое ужимается, чтобы освободить место новому.

**Ленивая загрузка.** Skills и MCP-серверы не занимают контекст целиком: агент видит только их имена и описания, а полное содержимое подгружается лишь тогда, когда оно реально понадобилось для задачи.

**Делегирование субагентам.** Объёмное исследование уходит субагенту с собственным контекстом, а в основное окно возвращается только краткий итог. Главный контекст остаётся чистым.

**Внешнее состояние.** Todo-списки, планы и промежуточные заметки хранятся вне окна контекста; агент обращается к ним по мере необходимости, а не держит всё в «памяти» постоянно.

## Надёжность

Работа с реальными проектами требует, чтобы система была устойчива к ошибкам — своим и чужим.

**Debug loop.** Упавший тест или сломанная сборка — не остановка, а переход в цикл отладки: прочитать ошибку → найти причину → исправить → проверить снова. Число итераций ограничено, чтобы агент не зациклился.

**Ограничение деструктивных действий.** Опасные операции (удаление файлов, незнакомые shell-команды) требуют подтверждения или запрещены вовсе. Разделение ролей — например, read-only агент для планирования и полноправный агент для реализации — снижает риск случайных повреждений.

**Наблюдаемость.** Каждый вызов инструмента логируется: пользователь видит, что происходит на каждом шаге, и может вмешаться. Hooks позволяют автоматизировать реакции на события — например, прогонять форматтер после каждой правки файла.

**Границы автономности.** Агент — помощник, а не замена разработчику: рутину он берёт на себя, но ключевые решения остаются за человеком. Режимы автономности регулируют этот баланс — от «только покажи план» до «действуй самостоятельно».

## Как это применяется в нашем проекте

Теория выше в этом репозитории превращена в конкретные артефакты:

- **`AGENTS.md`** — часть Config агента: стек, структура, команды и правила поведения, которые попадают в контекст в начале каждой сессии.
- **`docs/architecture.md`** — архитектура приложения: слои фронтенда, бэкенд на Fastify, поток данных и команды разработки. Её читают, когда нужно понять, куда класть код и как связаны части системы.
- **`docs/conventions.md`** — конвенции кодирования с примерами: именование, экспорты, стиль, структура компонентов. Её читают перед написанием нового кода.

Правило проекта: **перед крупными изменениями — сначала прочитать соответствующий файл в `docs/`**. Это практическое применение управления контекстом: вместо того чтобы держать всю теорию в `AGENTS.md` (и в окне контекста), детали вынесены во внешнее хранилище и подгружаются лениво — только когда нужны для текущей задачи. А проверки из execution loop закреплены командами: после правок агент обязан прогнать `npm run typecheck`, `npm run lint` и `npm test`, прежде чем считать задачу выполненной.

### Артефакты на базе этой теории

В проекте поверх принципов выше построены конкретные хранилища и инструменты:

- **Процессные скиллы** (`.agents/skills/<name>/SKILL.md`) — повторно используемые workflow, которые агент подгружает через `skill` tool по триггер-фразам (всего 83 директории: проектные процессные + upstream-набор, манифест — `skills-lock.json`):
  - `interview` — задать 3–7 уточняющих вопросов **до** начала реализации нетривиальной задачи.
  - `plan` — превратить задачу в атомарный пронумерованный чек-лист с проверками.
  - `ponytail` — проверка «можно ли решить без новой абстракции/зависимости/файла».
  - `tdd` — сначала failing-тест, потом минимум кода, потом рефакторинг.
  - `verify` — финальный прогон `lint`/`typecheck`/`test`/`build` перед отметкой задачи как «готово».
  - `commit-push` — стейджинг → Conventional Commits → пуш.
  - `apply-design` / `apply-design-v2` — внедрение дизайн-пакетов v1 (история) и v2 «Мята и солнце» (текущий).
  - `telegram-bridge` — согласования с телефона (`telegram-bot/`, вне git).
- **Долговременная память решений** (`docs/adr/`) — Architecture Decision Records в формате Nygard, индекс — `docs/adr/README.md`, шаблон — `docs/adr/template.md`. Один ADR = одно архитектурное решение, переживает любое `/compact`.
- **Состояние проекта** (`MEMORY.md` в корне) — версии зависимостей, текущие результаты проверок, раздел «Что осталось» из roadmap.

### Гигиена контекста

Правило проекта явно зафиксировано в `AGENTS.md` (раздел `## Hygiene of context window`): **после двух неудачных итераций одной и той же проверки (`lint`/`typecheck`/`test`/`build`) агент останавливается и спрашивает пользователя через `question(...)` или возвращается к скиллу `interview`.** Логика та же, что у debug-loop в этой теории, но с явной границей: 2 неудачи → reset подхода, не третья попытка.

### MCP-инструменты

В `opencode.jsonc` подключён MCP-сервер `shadcn` (пакет `shadcn`, запускается как `npx -y shadcn@latest mcp`), который даёт агенту доступ к каталогу компонентов через `components.json`. Подробности, fallback-политика и правила добавления новых MCP — в `docs/mcp.md`.
