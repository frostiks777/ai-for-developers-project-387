# Техническое задание и логика реализации: Веб-сервис «Календарь слотов бронирования»

## 1. Обзор проекта

Проект представляет собой интерактивный веб-сервис для управления доступностью и бронирования временных интервалов (слотов) для встреч, консультаций или менторских сессий (аналог Calendly / Google Calendar Appointment Scheduling).

Сервис решает две ключевые задачи:
1. **Для организатора (Host/Admin):** Настройка рабочего расписания, генерация слотов, управление бронированиями.
2. **Для клиента (Guest/User):** Просмотр доступных дат и времени, выбор и бронирование слота без конфликтов расписания.

---

## 2. Пользовательские роли и сценарии (Use Cases)

### 2.1. Организатор (Хост / Администратор)
- Задает общие параметры доступности (рабочие дни недели, рабочие часы, шаг слота: 15 / 30 / 60 мин).
- Задает буферное время между встречами (buffer time, например, 10 минут на перерыв).
- Указывает минимальное время предупреждения перед бронированием (например, нельзя забронировать менее чем за 2 часа до начала).
- Блокирует определенные даты или часы (отпуск, личные встречи).
- Просматривает список запланированных встреч и отменяет их при необходимости.

### 2.2. Клиент (Гость)
- Переходит по публичной ссылке организатора.
- Видит интерактивный календарь с активными (доступными) датами.
- Выбирает дату $\rightarrow$ отображается список доступных временных интервалов с учетом часового пояса.
- Выбирает свободный слот $\rightarrow$ заполняет контактную форму (Имя, Email, Примечание/Тема).
- Подтверждает бронирование $\rightarrow$ получает подтверждение на экране и email-уведомление (опционально: `.ics` файл для календаря).

## 3. Архитектура и структура страниц (UI/UX)

### Экран 1: Публичная страница бронирования (`/book/:hostId`)
1. **Левая колонка / Инфо-блок:**
   - Аватар и имя специалиста / организатора.
   - Название встречи (например, «30-минутная консультация»).
   - Длительность встречи и формат (Google Meet, Zoom, офлайн).
   - Селектор часового пояса (по умолчанию определяется автоматически через браузер пользователя).
2. **Центральная колонка / Календарь:**
   - Сетка текущего месяца с переключением месяцев (Prev/Next).
   - Неактивные дни (прошедшие даты, выходные дни специалиста, полностью занятые дни).
   - Выделенный выбранный день.
3. **Правая колонка / Список слотов:**
   - Появляется при выборе даты.
   - Список карточек со временем (например: `10:00`, `10:30`, `11:00`).
   - Кнопка подтверждения выбранного времени («Подтвердить» / «Далее»).

### Экран 2: Форма подтверждения бронирования (Модальное окно или отдельный шаг)
- Сводка выбранного времени: «Четверг, 24 сентября 2026, 14:00 - 14:30 (GMT+3)».
- Поля ввода:
  - Имя (обязательное).
  - Email (обязательное, валидация формата).
  - Телефон или ник в Telegram (опционально).
  - Комментарий / Вопрос к встрече (опционально, multiline).
- Кнопка «Забронировать».

### Экран 3: Экран успеха (Success Page)
- Статус: «Встреча успешно запланирована!».
- Кнопки добавления события: «Добавить в Google Календарь», «Скачать .ics».
- Ссылка на отмену или перенос (Reschedule/Cancel link).

### Экран 4: Панель управления организатора (`/dashboard`)
- Вкладка **«Календарь встреч»**: просмотр всех броней на день/неделю.
- Вкладка **«Настройки доступности»**:
  - Чекбоксы дней недели (Пн–Вс).
  - Временные диапазоны для каждого дня (например, Пн: 09:00 - 13:00, 14:00 - 18:00).
  - Длительность слота ($SlotDuration \in \{15, 30, 45, 60\}$ мин).
  - Буфер между слотами ($Buffer \ge 0$).

## 4. Логика генерации и валидации слотов (Backend / Core Logic)

### 4.1. Алгоритм генерации доступных слотов

Для выбранной даты $D$:
1. **Проверка глобальной доступности дня:**
   - Если день недели $DayOfWeek(D)$ не входит в рабочий график организатора $\rightarrow$ вернуть пустой список.
   - Если дата $D$ попадает в список исключений (отпуск/выходной) $\rightarrow$ вернуть пустой список.

2. **Формирование базовых интервалов:**
   - Взять рабочие окна организатора на этот день, например: $[W_{start}, W_{end}]$.
   - Разбить окно на потенциальные слоты с шагом $Step = SlotDuration + Buffer$.
   - Потенциальный слот $i$: $[S_i, E_i]$, где $E_i = S_i + SlotDuration$.

3. **Фильтрация по существующим бронированиям:**
   - Получить все подтвержденные бронирования $B$ организатора на дату $D$:
     $$B = \{ [b_{start}, b_{end}] \}$$
   - Слот $[S_i, E_i]$ считается **недоступным**, если существует пересечение с любым активным бронированием:
     $$S_i < b_{end} \quad \text{и} \quad E_i > b_{start}$$

4. **Фильтрация по текущему времени (Lead Time):**
   - Если $D$ — сегодняшний день, исключить слоты, у которых:
     $$S_i < CurrentTime + MinNoticeTime$$

5. **Преобразование часовых поясов (Timezone Handling):**
   - Все временные метки в БД хранятся строго в **UTC** (ISO 8601).
   - Преобразование в локальное время пользователя выполняется на клиенте или при сериализации ответа с учетом переданного таймзона.

### 4.2. Обработка состояния гонки (Race Condition / Double Booking)

Чтобы два пользователя не могли одновременно занять один и тот же слот:
- **Уровень БД:**
  - Транзакция с уровнем изоляции `SERIALIZABLE` или использование блокировок (`SELECT ... FOR UPDATE`).
  - Уникальный составной индекс или exclusion constraint (PostgreSQL `tsrange` с оператором `&&` для проверки пересечений диапазонов времени):
    ```sql
    ALTER TABLE bookings 
    ADD CONSTRAINT prevent_overlapping_bookings 
    EXCLUDE USING gist (
      host_id WITH =,
      tstzrange(start_time, end_time) WITH &&
    ) WHERE (status != 'cancelled');
    ```
- **Уровень приложения:** Возврат HTTP-статуса `409 Conflict`, если слот уже перехвачен другим пользователем во время отправки формы.

## 5. Схема базы данных (ERD)

### Таблица `hosts` (Организаторы)
- `id` (UUID, PK)
- `name` (VARCHAR)
- `email` (VARCHAR, Unique)
- `timezone` (VARCHAR, e.g. `'Europe/Moscow'`)
- `created_at` (TIMESTAMP)

### Таблица `availability_rules` (Правила доступности)
- `id` (UUID, PK)
- `host_id` (UUID, FK -> `hosts.id`)
- `day_of_week` (SMALLINT, 0-6: Вс-Сб)
- `start_time` (TIME, e.g. `09:00:00`)
- `end_time` (TIME, e.g. `18:00:00`)
- `slot_duration_minutes` (INT, default: 30)
- `buffer_minutes` (INT, default: 10)

### Таблица `bookings` (Бронирования)
- `id` (UUID, PK)
- `host_id` (UUID, FK -> `hosts.id`)
- `client_name` (VARCHAR)
- `client_email` (VARCHAR)
- `client_notes` (TEXT, nullable)
- `start_time` (TIMESTAMPTZ)
- `end_time` (TIMESTAMPTZ)
- `status` (ENUM: `'confirmed'`, `'cancelled'`)
- `created_at` (TIMESTAMPTZ)

## 6. Спецификация API (REST)

### Публичные эндпоинты:
- **`GET /api/v1/hosts/:slug/settings`**
  - Возвращает публичные данные хоста, длительность встреч и активные дни недели.
- **`GET /api/v1/hosts/:slug/slots?date=YYYY-MM-DD&timezone=UTC`**
  - Возвращает массив доступных слотов на выбранную дату:
    ```json
    {
      "date": "2026-09-24",
      "slots": [
        { "start": "2026-09-24T10:00:00Z", "end": "2026-09-24T10:30:00Z" },
        { "start": "2026-09-24T10:40:00Z", "end": "2026-09-24T11:10:00Z" }
      ]
    }
    ```
- **`POST /api/v1/bookings`**
  - Создает новую бронь.
  - Body: `{ "hostId": "...", "startTime": "...", "clientName": "...", "clientEmail": "..." }`
  - Ответы: `201 Created` / `409 Conflict` (слот занят) / `422 Unprocessable Entity`.

## 7. Рекомендуемый стек технологий

- **Frontend:** Next.js (React) + Tailwind CSS + Lucide Icons + date-fns / dayjs (для работы с таймзонами).
- **Backend:** Node.js (NestJS / Fastify) или Python (FastAPI).
- **База данных:** PostgreSQL (поддержка `tstzrange` и GiST индексов).
- **Очереди / Уведомления (опционально):** Redis + BullMQ для отправки напоминаний на почту за 1 час и 24 часа до встречи.
