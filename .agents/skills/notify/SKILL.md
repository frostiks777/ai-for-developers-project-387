# notify

Единая точка связи с пользователем: уведомление, вопрос с апрувом, ожидание ответа.
Одно событие уходит в **оба канала** — Telegram и Windows-тост.

## Почему один скрипт, а не две команды

Раньше уведомления слались двумя способами — `telegram-bot/notify.mjs` и `scripts/notify.ps1`.
Правило «в какой канал слать» жило в голове агента, и оно расходилось: то в чат, то тостом,
то оба сразу без причины. Пользователь просит уведомления **всегда в оба канала** — они
смотрят разные источники (телефон и компьютер), и одно и то же событие в них не путается.

`scripts/notify.mjs` убирает решение из головы агента:

| Проблема | Как решает скрипт |
|---|---|
| «В какой канал слать?» — решение каждый раз разное | По умолчанию **оба** канала: Telegram + тост. Отключить один явно: `--channel telegram` / `--channel toast` |
| Два вызова подряд на одно и то же событие | Ключ события (`--kind`) с окном подавления 10 минут: повтор гасится, код выхода `3` |
| Один канал недоступен (нет моста, не Windows) | Пропускает этот канал и отправляет второй, а не падает |
| Агент «забыл» дождаться ответа | `--wait <секунды>` ждёт строку с `qid` в `telegram-bot/decisions.jsonl` |

## Как отправить уведомление

```bash
node scripts/notify.mjs "Заголовок" "Текст" --kind <start|blocker|release|info>
```

Уведомление уходит **и в Telegram, и тостом** — отдельного выбора канала не нужно.
`--kind` — ключ подавления повторов, выбирай по смыслу события:

- `start` — старт работы над задачей;
- `blocker` — упёрся в вопрос, без пользователя не двинуться;
- `approve` — ждём вашего решения по pull request (см. выше);
- `release` — задача доведена до конца, push/CI зелёные;
- `info` — всё прочее (по умолчанию).

Одно и то же событие **не слать дважды**: сначала `start`, потом через минуту тот же `start` — скрипт сам от suppresses.

## Как спросить и дождаться решения

```bash
node scripts/notify.mjs "Нужно решение" "Короткий вопрос?" --kind blocker --id q123 --wait 600
```

В Telegram приходят кнопки ✅/⛔ (и `/approve q123` / `/deny q123`).
Скрипт блокируется, пока пользователь не ответит, и печатает `решение q123: approve|deny`.

| Код выхода | Значение | Что делать |
|---|---|---|
| `0` | Отправлено, решение получено | Действовать по решению |
| `1` | Telegram не отправил | Метка дедупликации не записана, можно повторить; если повтор не помог — спросить в чате |
| `2` | Решение не пришло за отведённое время | Не выдумывать решение. Повторить вопрос с новым `--id` или спросить в чате |
| `3` | Событие подавлено как дубль | Ничего не делать, уведомление уже ушло |

## Когда уведомлять

Ровно четыре случая — больше не нужно:

1. **Старт работы над задачей** — коротко: что делаю, номер issue.
2. **Блокер или вопрос** — только то, где ответ пользователя меняет ход работы.
3. **Ждётся ваше решение по pull request** — см. следующий раздел: без уведомления пользователь не знает, что нажать.
4. **Релиз** — задача доведена до конца, пуш сделан, CI зелёные.

На каждый шаг, каждое промежуточное действие — **не слать**.

## Обязательное уведомление: ждётся решение по PR

Агент часто упирается в ожидание: PR открыт, а согласовать его может только человек. Молча
ждать нельзя — пользователь не видит, что нажать, и цикл выглядит зависшим бесконечно.

**Обязательное правило: как только работа упирается в чужое решение — уведомить с `--id` и ждать `--wait`.**

```bash
# 1. Узнать, что ждём: открытые PR и их состояние
gh pr list --state open --json number,title,author,isDraft,url

# 2. Уведомить с кнопками и ждать ответа
node scripts/notify.mjs "Нужно согласовать PR" "PR #24 chore(main): release 1.1.0 — https://github.com/.../pull/24. Мерджить?" \
  --kind approve --id pr24 --wait 900
```

Текст уведомления обязан содержать **три вещи**, иначе пользователь не поймёт, что делать:

| Что | Пример |
|---|---|
| Что именно | номер PR и название |
| Где посмотреть | ссылка на PR |
| Что нужно сделать | «мерджить», «посмотреть ревью», «ответить на замечание» |

Когда ждёте решение:

- **Release-PR от release-please** (`chore(main): release X`) — он ждёт мерджа; после мержа версии и changelog обновятся.
- **PR агента с замечаниями авторевью** — ждёт вашего ответа на замечание или аппрува.
- **PR, где CI красный** — сначала чинить код, а не звать человека; уведомлять только когда нужен человек.

**Не крутиться в цикле.** Если апрув не пришёл (код `2`):

1. не повторять тот же вопрос с тем же `qid` — пользователь его уже видел;
2. продолжить то, что не зависит от ответа (проверки, правки документации, другие задачи);
3. если без ответа работа встала — прислать одно уточняющее сообщение с **новым** `--id` и пометкой «жду ответа на прошлый вопрос», и дальше ждать в чате, а не в бесконечном ретрае.

## Правила содержания

- По-русски, коротко: заголовок — до 5 слов, текст — до двух строк.
- **Никогда** не слать секреты: токены, `DATABASE_URL`, `ADMIN_PASSWORD`, `OPENCODE_API_KEY`.
- Вопрос формулируется так, чтобы на него можно было ответить «да» или «нет». Открытый вопрос без вариантов апрува не отправляй.
- Апрув — это разрешение на конкретное действие, а не согласие «на всё дальнейшее».

## Каналы

`--channel both` (по умолчанию) | `telegram` | `toast`

- `both` — **всегда оба канала**: Telegram (`telegram-bot/notify.mjs`, нужен `.env` и живой `.bot.pid`) и Windows-тост (`scripts/notify.ps1`, требуется UTF-8 BOM в файле, иначе PowerShell 5.1 ломает кириллицу). Отсутствие одного канала не мешает второму: недоступный пропускается молча.
- `telegram` / `toast` — отключить один канал. Осознанно, когда канал заведомо недоступен или пользователь просил только одно.

## Запрещено

- Вызывать `telegram-bot/notify.mjs` и `scripts/notify.ps1` напрямую — только `scripts/notify.mjs`, иначе теряется подавление повторов.
- Отключать канал без причины (`--channel telegram` / `--channel toast`) — по умолчанию оба, всегда.
- Выдумывать решение пользователя, если строки с `qid` нет в `telegram-bot/decisions.jsonl`.
- Класть `telegram-bot/` (`.env`, `*.jsonl`, `.bot.pid`, `.notify-state.json`) в git — папка уже в `.gitignore`.
